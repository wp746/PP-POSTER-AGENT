# 风格库与元提示词引擎设计

> 本文为系统设计规格。当前未收到用户的风格提示词或风格参考；文末仅有一项原创、待试验的示例，不代表已经学习、出图或通过模型验证。

[主规格](../Product-Spec.md)定义总规则；本文件负责细化风格机制，不降低其事实、主体与验收要求。

## 1. 风格库解决什么问题

用户提供一次优秀的海报提示词或参考后，系统提取其中可迁移的设计方法，形成可重复调用、可调整、可验证的风格包。以后选择该风格时，系统用本次产品或活动的信息重新构图，不能把旧案例的菜名、城市、日期、地标、品牌和标语带进来。

风格包保存的是规则和可变范围，不能只是给一段旧提示词换标题。它需要回答：主体如何占据画面，观看顺序如何形成，文字如何组织，背景如何提供空间，光线与色彩如何服务主体，以及在信息增多、比例变化时如何调整。

系统有两条入口，最终使用同一个约束检查和提示词编译流程：

- **自主创意**：根据品类、活动主题和已核实信息，生成本项目的临时设计方案。临时方案不自动成为全局风格。
- **选择风格**：加载一个有版本的风格包，结合美食或活动适配器，以及本次内容约束，生成项目方案。

新增常规风格通过新增数据包完成，不改核心代码。若新风格需要系统尚不具备的能力，例如曲面贴字、精确三维投影或特殊文字遮挡，先标记所需能力；不能把一项缺失的渲染能力伪装成提示词问题。

## 2. 风格家族、预设与项目模板

| 层级 | 保存内容 | 示例 | 不应保存的内容 |
| --- | --- | --- | --- |
| 风格家族 | 稳定的构图语法、空间方法、字体角色、光色逻辑、材质语言 | 「暖调纵深编辑」：暖色空间、实体承托、标题与主体形成主次、前后景分层 | 固定菜名、固定地标、某次活动日期 |
| 可执行风格包 | 家族下的版本化执行单元，包含规则、元提示词、适配器、兼容性、验证记录与预设 | 「暖调纵深编辑」生产包 v0.1.0 | 把某一次项目参数视为全局默认 |
| 风格预设 | 家族内已命名的一组参数，保留同一设计语法 | 「烘焙·柔光横向留白」「赛事·暖光聚焦」 | 无依据的商业卖点、未授权品牌元素 |
| 项目模板 | 某个业务场景的字段、尺寸和布局规则，可引用家族与预设 | 「门店新品发布·竖版」「城市赛事招募·横版」 | 把一次用户私有内容变成所有人共享的默认值 |
| 项目实例 | 本次事实、素材、参数、版本与输出 | 某门店某产品的本次海报 | 自动回写全局风格规则 |

「红色」「高级」「电影感」本身不足以构成风格家族；至少要有可识别的构图方法与文字组织规则。相同结构只改颜色或材质，优先作为同一家族的预设，避免风格列表不断膨胀。

层级统一为家族 → 风格包 → 预设。项目模板引用固定的风格包版本与预设，项目实例保存本次输入和产物。业务类型是筛选与适配维度，不因同时支持美食和活动而复制风格包身份。

前台只展示风格名称、示例、适用场景、信息容量和是否已验证。来源记录、编译结构和内部评分留在管理端。没有实际生成样张时，前台明确显示「待试验」，不能用其他风格的图片充当样张。

## 3. 用户投喂材料后的沉淀流程

### 3.1 接收与来源登记

可接收提示词正文、参考图、链接，以及用户对「想保留什么」的说明。先保留原件并建立来源记录，再进行分析；来源原件默认只在用户自己的资料空间内可见。

最小记录：`source_id`、材料类型、原文或文件定位、来源链接（如有）、提供时间、内容指纹、用户备注、访问状态、使用范围。使用范围不明时记录 `unknown`，不自行宣称素材或字体具有商用许可，也不因此阻止抽象设计方法的分析。若来源含账号、私人联系方式或密钥，只登记必要出处，进入风格包的内容必须脱敏。

只有提示词、没有图片时，分析结论属于「文本推断」，不能声称已验证其真实画面效果。链接不可访问时，保留链接并说明缺失内容；可以继续分析用户已经提供的文本，不能假装看过网页。需要以具体图片为依据的结论必须有实际可查看的图片。

### 3.2 拆解成可核查的设计规则

每条规则需带 `evidence`，取值为 `explicit_text`（原文明确）、`visible_reference`（参考中可见）、`inferred`（分析推断）或 `original_extension`（系统扩展）。原文描述与图像表现冲突时分别记录，不能混合成确定事实。

| 拆解维度 | 要提取的规则 | 要剥离的案例信息 |
| --- | --- | --- |
| 事实变量 | 标题、副标题、口号、卖点数量、行动指令等字段角色 | 旧菜名、旧活动名、日期、地址、电话、价格、未经本次提供的功效与资质 |
| 版式语法 | 主体与文字占比、视觉中心、阅读顺序、对齐方法、网格、留白与安全区 | 只有原尺寸才成立的固定像素坐标 |
| 媒介与材质 | 摄影、拼贴、纸张、金属、剪纸等表达方法及强度 | 原案例特有且不应复用的图案、角色与徽标 |
| 字体系统 | 标题/正文/数字角色、字重、宽窄、字距、行距、最大行数、授权字体替代方案 | 把某商业字体名称视作已经获得字体文件与许可 |
| 背景与空间 | 前中后景、实体承托、遮挡关系、清晰度梯度、空间透视 | 原案例特定场地、未经本次确认的地标 |
| 色彩 | 主色/辅色/强调色的角色、明度层级、面积关系、与主体的对比 | 无条件继承原案例品牌色 |
| 光线 | 光源方向、软硬、轮廓光、阴影、色温及反射逻辑 | 会改变当前食物成熟度、颜色或材质事实的光色处理 |
| 可变参数 | 比例、主体占比、标题区、装饰密度、景深、色温等允许范围 | 任意改变产品数量、容器、品牌标志等受保护字段 |

一句「世界级排版」不能作为验收规则。要翻译为可检查的设计意图：标题能否第一眼识别、信息是否有主次、字体角色是否一致、边距与对齐是否有规律、主体轮廓是否清楚、背景是否支持而非争夺注意力。

### 3.3 去案例化与独立命名

1. 把来源专名、数字、地点、宣传主张、标志和角色列入 `source_case_tokens`。此表留在来源分析记录中，不传给图像模型。
2. 用字段角色替换案例值。例如把「某某烘焙·新品上市」拆成 `product_name` 与 `campaign_intent`；不能只把品牌名替换成「你的品牌」。
3. 把具体场景转成条件规则。例如「古城城墙」只能变成「在活动所在地已核实的视觉符号」，不能成为风格的永久背景。
4. 生成独立风格名称与一段结构描述，说明保留的设计原理和新增的通用规则。
5. 对编译产物做来源泄漏扫描：禁止出现未被本次事实白名单重新授权的源案例信息。若原来源地名恰好也是本次活动地名，必须来自本次资料或核实记录，而不是来源继承。

模型面对的是本次完整视觉指令，不使用「参照某网上海报」「按照原案例替换」「照着某设计师的图」等依赖来源的表达。确实需要参考图传入模型时，单独列出该图可借鉴的维度，并禁止它覆盖产品或品牌锁定素材。

### 3.4 去重与归类

去重依据为布局语法、文字组织、空间关系、光色逻辑和材质表达，不以风格名字或提示词字面相似度单独判断。

- 与既有风格仅颜色、材质、装饰密度不同：建议新增预设。
- 对既有规则有清晰改进：产生新版本，并保留差异说明。
- 主体与标题的组织方式、空间结构都有明显不同：可新增家族。
- 无法判断：保留为草稿，展示并列比较，不强行合并。

自动去重只提供候选与解释。已投入生产的风格不能因自动判断被覆盖或删除。

## 4. 共用骨架与两个独立适配器

共用骨架负责主体、标题、次级信息、背景、光色、空间和输出比例。适配器决定哪些内容可以改、哪些元素有真实依据，以及当前品类如何表达。

### 美食适配器

- 输入必须包含可查看的原始照片和产品 DNA 记录。记录原料/成品的可见外观、数量、形状、层次、排列、表面状态、容器与装盘；区分 `VISIBLE / INFERRED / MISSING`。
- 默认 `STRICT_2D_LOCK`：不得通过大幅换角度显露原图未提供的结构。原料名称不能成为新增可见原料的授权。
- 可调整区包括背景、环境光、局部对比和不改变食物真实色泽的色彩整理；容器和装盘按项目锁定。
- 原料做装饰、热气、切面、汁液飞溅、散落配料都可能产生新的产品事实，必须有本次依据与授权。不能把来源风格中的草莓、辣椒、蒸汽固定植入所有食物。
- 字体、材质和色调依据具体品类适配；烘焙、冷饮、火锅、轻食不能共享无条件的黑金、书法或古风默认。
- 若保真要求与风格冲突，优先调低风格强度、移动背景元素或保持原视角。提示词声明锁定不等于已做到锁定，须由实际结果检查确认。

### 活动适配器

- 输入包含活动事实表、主题、活动类别、受众、行动目标、主办方资料、品牌与 IP 素材，以及地点研究结果（如需要）。
- 先形成主题与核心视觉概念，再选择与之匹配的风格参数。不能先塞满城市元素，再事后找活动含义。
- 城市视觉符号只能取自已核实的 `place_motifs`。记录名称、地域关联、来源和使用方式；一个主要符号加少量辅助符号通常更容易形成清晰主题，数量由构图与活动含义决定。
- 「所在地相关」不等于「举办场地」。例如城市地标可以作文化意象，但不能误写成比赛场馆，也不能暗示地标机构参与主办。
- 活动文字、组织关系、logo、吉祥物和 IP 具有独立锁定规则；风格不能改变名称、角色身份、logo 结构或主办/协办关系。

约束优先级从高到低：**已确认事实与用户硬约束 → 产品 DNA / 品牌 / IP 锁定 → 信息可读性与必要字段 → 当前主题与业务适配 → 风格家族规则 → 预设参数与装饰偏好**。同层冲突需要明确解决；系统不能悄悄牺牲硬约束。仅当缺失信息确实阻止当前选择时向用户提出具体问题。

## 5. 风格包字段

采用 JSON、YAML 或数据库记录均可，但字段语义必须一致。以下是可直接实现的最小结构；证据文件与实际图片放在独立资源目录，通过 ID 关联。

```yaml
style_id: stable-unique-id
family_id: stable-family-id
name: 用户可见名称
version: 0.1.0
status: draft                 # draft / experimental / validated / disabled
description: 构图与空间方法的简短说明
origin:
  type: original              # original / distilled / mixed
  source_ids: []
  analysis_record_id: analysis-xxx
  usage_scope: private
rules:
  composition: []
  typography: []
  color: []
  lighting: []
  depth_and_background: []
  materials: []
  forbidden_transformations: []
parameters: {}                # 类型、默认值、允许范围及控制的视觉效果
adapters:
  food: {}
  event: {}
compatibility: []             # 业务、素材前提、比例、文字容量、状态、理由
requirements:
  input_assets: []
  renderer_capabilities: []
presets: []
prompt_template_id: template-xxx
test_cases: []
validation_record_ids: []
change_note: 首次草稿
previous_version: null
```

每个规则项至少具有 `id / rule / evidence / source_ref / strength`。`strength` 取 `required` 或 `preferred`；风格内部的 `required` 仍然低于事实与产品/品牌约束。渲染器能力字段只引用已实现或已验证的能力名，不能写一个字段就宣称模型支持。

参数分为三类：用户可选（如氛围、装饰密度）、系统推导（如标题区尺寸、字数容量）、受保护只读（如锁定主体角度、品牌色、logo 比例）。用户界面不能用一个「创意强度」滑杆同时解锁食物结构和背景设计。

## 6. 兼容性与失败处理

兼容性按「风格版本 × 业务 × 输入条件 × 比例 × 信息密度」记录，不能只有一个全局 PASS。每个组合分别保存 `design_fit = supported / conditional / unsupported` 与 `verification_status = untested / passed / failed`。规则适配不代表实测通过；验证记录还需绑定实际供应商/模型能力版本、主体保护策略和文字渲染路径。

| 条件 | 自动判断与处理 | 不能做的事 |
| --- | --- | --- |
| 竖版、常规短标题、3—5 个短卖点 | 按该比例布局规则编译；检查标题、主体与信息区 | 默认所有比例共享同一坐标 |
| 长标题或卖点文字较多 | 先用目标字体真实测量并重排，启用预设的信息区扩展；仍溢出时给出精简建议或第二张信息海报方案 | 缩小到不可读、擅自删掉必填事实、未经授权自动增加成品数量 |
| 竖版改横版 | 切换对应布局语法，重新分配主体和标题位置，重新检查 DNA、遮挡和字区 | 裁掉盘沿、拉伸食物、只把竖版成图横向裁切 |
| 原图主体已被截断或有严重遮挡 | 标出不可见结构；按可见轮廓做保守构图，完整结构为硬要求时索取补充照片 | 宣称补画部分与真实产品一致 |
| 缺少原始食物图 | 可完成文案整理和方案准备，停止依赖原图的保真生产 | 用风格参考中的食物顶替用户产品 |
| 风格依赖俯视，但原图是平视 | 标记条件不兼容；用保持视角的变体或推荐可用风格 | 为满足风格无授权地重建不可见角度 |
| 缺少必须出现的 logo / IP 原件 | 先安排占位区域并整理其余设计；最终品牌版本等待所需素材 | 用生成模型猜画正式 logo、从模糊截图假称恢复准确原件 |
| 品牌色与家族主色冲突 | 保留品牌硬约束，调整背景和辅助色，记录为变体 | 自动改品牌标志颜色 |
| 需要真实地点却无研究结果 | 继续做抽象主题构思；暂不引入具体地标，完成核实后再编译 | 从风格原案例继承地标或捏造当地建筑 |
| 风格所需能力尚未验证 | 管理端显示待试验；可以生成已授权的试验产物并单独验收 | 将试验功能承诺为稳定生产 |

文字容量不是统一的「最多 15 个字」。每种比例和字体角色保存建议行数、最小字号与字区；编译时根据实际文字、字体、输出分辨率测量。没有字体文件或测量器时只能给保守估算，不能称为排版校验通过。

## 7. 提示词编译顺序

1. **冻结输入快照**：选定本次事实版本、原图与品牌素材、DNA 记录、目标比例、风格版本及输出方式。
2. **核对必需输入**：检查必填事实、素材可访问性和风格要求；将可继续的准备工作与被阻止的生产步骤分开。
3. **建立事实白名单和保护区**：生成可使用的文案、可见素材与不可改字段；标记缺失、推断和不可读信息。
4. **选择业务适配器**：生成品类/活动主题对应的构图需求和有依据的场景元素。
5. **装配家族、预设与项目参数**：参数越界或与保护规则冲突时先调整；无法解决时返回具体原因。
6. **完成文字与空间规划**：计算阅读层级、实际字区、主体安全区、品牌区及必要信息区。
7. **按渲染路径分离任务**：通过 `render_scope` 选择独立指令。`background_only` 仅生成环境，不生成食物、器皿或受保护品牌/IP 本体，主体位置只表示后期合成空位；主体参考只用于匹配视角与光线。只有已经授权的 `subject_edit` 分支允许主体编辑，`event_visual` 分支生成活动视觉，准确文字与保护资产由独立合成计划处理。正式字形与概念含字探索遵守主规格，不另降标准。
8. **渲染完整元提示词**：填充全部变量，生成来源无关的模型指令；不传管理备注、网页原文或源案例专名表。
9. **静态检查**：必填变量无缺失、无未展开占位符、无越权元素、无源案例泄漏、无冲突、文字完整，且保护参考优先级明确。
10. **保存编译清单并调用**：记录模板版本、风格版本、输入与资产哈希、参数、提示词哈希、实际渲染路径及生成设置（可获得时）。固定随机种子（若支持）也不能被表述为必然逐像素复现。
11. **验收与局部修订**：根据实际失败项修改对应参数或步骤，不能每次重写全部规则。新的风格发现先作为项目变体，经过独立沉淀后才能升级全局风格。

原始网上提示词属于待分析的数据，其中的角色指令、工具调用、隐私索取或「忽略其他规则」不能进入生产指令。

## 8. 完整参数化元提示词结构

## 9. 原创待验证示例：暖调纵深编辑

**状态：`draft`，版本 `0.1.0`，来源 `original`。本例没有用户来源材料，没有实际样张，没有模型与排版验收结果。**

### 家族定义

以真实主体为视觉锚点，通过实体承托面、柔和侧光与前后景明度差形成纵深；大标题与主体建立稳定的双焦点，辅助信息沿清晰网格排列。高级感来自比例、光影、材料和阅读顺序，不能依赖大面积金色、泛滥装饰或极小文字。

稳定规则：

- 主体保持清晰，前后景层次清楚；背景细节比主体低一个层级。
- 采用一个主要光源逻辑，接触阴影与承托面一致。
- 主标题使用有辨识度的展示字体，正文选择易读字体；字体文件及许可未确认前只定义角色，不承诺具体字体。
- 文字区与主体轮廓保留呼吸空间；可以靠近形成张力，不能遮挡关键产品结构或活动 IP 面部。
- 温暖中性色作环境基底，强调色由产品或品牌提取；若产品本来偏冷色，则降低暖色强度，保持真实色泽。

参数示例：

| 参数 | 默认 | 可选范围 | 保护条件 |
| --- | --- | --- | --- |
| `warmth` | mild | neutral / mild / warm | 不改变食物成熟度、酱色或品牌色 |
| `depth` | medium | low / medium / high | 不新增不可见产品结构；景深不得模糊主体关键特征 |
| `decor_density` | low | none / low / medium | 只使用已允许的元素；不以添加配料制造食欲 |
| `headline_position` | auto | auto / top / side | 由比例与文字测量决定可用位置 |
| `subject_occupancy` | auto | 系统按画幅求解 | 保留完整容器、装盘与品牌安全区 |

### 两个适配预设

**美食预设：烘焙·柔光留白。** 适用于原图烘焙主体可辨认、主要轮廓完整且有合适视角的项目。保持数量、表皮、夹层、盘具和摆放关系；背景可使用中性材质承托与远处柔和明暗变化。仅可依据原图强化可见的酥脆或柔软质感，不新增切面、面粉、奶油或水果。3:4 与 4:5 为待试验布局，横版需要独立重排与验收。

**活动预设：文化体验·主题聚焦。** 适用于文化体验、展览、城市生活类活动。活动主题是主视觉中心，所在地符号只作为有依据的空间线索；若无已核实地点素材，使用与主题相关的抽象空间。高密度议程、大量赞助商或强调强烈速度感的竞技赛事，暂不作为此预设的优先场景。

示例兼容记录：

| 组合 | 设计适配状态 | 实际验证 |
| --- | --- | --- |
| 烘焙、轮廓完整、短标题、3:4 | conditional：需原图与文字测量 | untested |
| 同一美食、16:9 | conditional：需横版布局 | untested |
| 文化体验、简短核心信息、4:5 | conditional：需主题与素材 | untested |
| 十余行议程与多排赞助商、单张窄幅海报 | unsupported：超出当前信息容量设计 | 未测试 |
| 平视食物要求改成完整俯视、严格 DNA 锁定 | unsupported：输入与视角要求冲突 | 不进入生成 |

这项风格可以展示设计说明，但在完成真实样张验收前不能带有「已验证」标记。未来收到用户材料后，按同一流程生成新的草稿或预设，而非默认把本例当作用户已认可的审美基准。

## 10. 版本、验证与回滚

版本不可原地覆盖。修正文案说明且不影响输出可升补丁版本；新增预设或保持旧参数语义的能力可升次版本；构图语法、参数含义、默认值或兼容性发生破坏性变化时升主版本。只要生产提示词或渲染规则改变，都需要留下新版本与变更说明。

状态与证据分开管理：

- `draft`：完成来源拆解和规则说明，可检查结构；没有实际效果承诺。
- `experimental`：可用于明确标注的试验任务，保留每次输入、输出和失败项。
- `validated`：至少一个明确的兼容组合通过下表全部适用验收，且同组合至少有两个内容不同的真实项目证明风格一致性。验证标签显示业务、比例、信息密度、素材条件及渲染路径，不能扩大到家族所有用法。生产选择必须命中 `verification_status=passed` 的具体组合，不能只检查包状态。
- `disabled`：停止新生产选择，保留历史工程和来源；已有项目可查看其固定版本，并由用户选择是否迁移。

回滚改变风格目录中的默认版本指针，不删除失败版本，不重新生成或覆盖旧成品。每个项目固定所用版本；全局升级不静默改变已完成项目。若希望复用旧设计，系统重载旧参数和素材；再次生成的图像仍可能有差异。

### 最小回归与验收

风格晋级验证应使用可追溯的真实样张；所有用例记录输入、版本、参数、输出、检查人/方法、失败项与修订次数。测试数量随承诺范围增加，不以一张最好看的成功图证明稳定性。

模型/供应商能力版本、主体保护策略、文字渲染路径或风格规则变化时，受影响组合的验证状态失效并重新验收；旧版本的证据保留，不静默移给新版本。

| 验收项 | 最低证据 | 通过条件 |
| --- | --- | --- |
| 去案例化 | 至少两个不同项目的编译产物与源案例字段检查 | 没有未授权专名、数字、地标或视觉符号泄漏 |
| 事实准确 | 文本清单与最终成品逐项对照 | 必填内容无漏项、无改写事实、无虚构新增；日期电话地址等准确 |
| 美食 DNA | 原图与真实输出的逐项视觉比较 | 锁定数量、轮廓、表面、容器、装盘关系无未接受变更 |
| 品牌 / IP | 原始文件与成品比较 | 标志比例、名称、身份、颜色及禁止遮挡区符合本次规则 |
| 字体与排版 | 字体可用性检查、实际尺寸预览及移动端缩略预览 | 无溢出截断、缺字、难辨正文，标题与行动信息层级清晰 |
| 比例迁移 | 每个宣称支持比例的真实样张 | 重排后主体完整、信息可读、安全区成立 |
| 边界条件 | 长标题、高信息密度及缺参考用例 | 正确重排或明确返回不兼容，不静默删事实、补画主体 |
| 风格一致性 | 同一兼容组合下至少两份内容不同的真实项目 | 内容已改变，仍能识别共同的构图、光色与文字组织方法 |
| 视觉质量 | 按设计意图人工审看并记录结果 | 视觉焦点、空间层次、光源、材质与品类一致，无明显伪影 |

OCR、像素相似度与自动视觉检查可以协助发现问题，不能单独证明食物结构、logo 或所有文字都正确。若产品 DNA 反复漂移，应切换到原图主体保留与背景/排版合成等可实现路径，或明确缩小可承诺范围；不能靠反复添加「绝对不变」宣称问题已解决。

## 11. V1 落地边界

V1 先实现风格包登记、双业务适配、参数校验、提示词编译、兼容性提示、版本固定与验收记录。风格数量可从零开始；不需要先假设一个庞大的通用风格目录。用户提供材料后，每次交付「拆解卡、候选家族/预设、去案例化规则、参数范围、兼容条件、待验收样张计划」，再依据任务授权安排真实试验。

完整闭环是：**材料进入 → 规则提炼 → 风格草稿 → 当前项目编译 → 真实试验 → 产品/事实/排版/视觉验收 → 限定范围验证 → 版本化复用**。

核心风险是把提示词存储当成设计沉淀、把语言中的 DNA 锁定当成图像结果保证、把一张样张扩展成所有品类与比例的能力承诺。系统应把这些差异直接体现在规则、版本、兼容记录和验收证据中。
